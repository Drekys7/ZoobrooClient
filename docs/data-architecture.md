# Источники данных

```text
Админка → публикация → manifest + PublishedZooMap + immutable assets
                                      ↓
                        MapRepository → MapLoader
                                      ↓
                              toVisitorMap → UI
```

## HTTP / сервер зоопарка

`HttpMapRepository` уже работает с публичным manifest. Сервер зоопарка может читать PostgreSQL, MySQL, SQLite или другую БД и выдавать тот же формат. Доступ к БД и секреты остаются на сервере. Переход от локальных файлов к API требует смены `VITE_MAP_MANIFEST_URL`, а не переписывания карты.

Порядок публикации: записать все ресурсы → JSON → проверить их доступность → последним заменить manifest. Файлы существующей версии не перезаписываются. В production используйте монотонные номера версий; локальная команда импорта использует v1 с разными SHA-256 и путями JSON. Клиент различает их по проекту, версии и SHA-256. Manifest не должен кешироваться надолго; для ресурсов с хешем используется immutable cache.

Manifest:

```json
{
  "zooId": "zoo-1",
  "projectId": "zoo-1",
  "schemaVersion": 1,
  "version": 42,
  "publishedAt": "2026-09-23T12:00:00.000Z",
  "contractUrl": "versions/42/map.json",
  "sha256": "<64 hex characters>"
}
```

Asset URLs в JSON разрешаются относительно файла JSON; `contractUrl`, `raster.previewUrl` и `raster.tileUrl` — относительно manifest. Допустимы HTTP(S), но не `asset://` и не временные `blob:`-ссылки админки.

Необязательный `raster` описывает оптимизированную доставку фона. Его `sourceAssetId` обязан совпадать с ID фоновой картинки в контракте. Тайлы привязаны к исходным пиксельным координатам, верхний левый угол — (0,0). При размере тайла 512 уровень `zoomOffset` соответствует исходным пикселям; более низкие уровни уменьшаются вдвое. `minNativeZoom = -zoomOffset`, `maxNativeZoom = 0`. Пример полностью заполнен в `public/data/manifest.json`.

Raster не входит в общий PublishedZooMap: это дополнение транспорта, которое сервер может не предоставлять. Для новой версии алгоритма сжатия/нарезки необходимо менять URL тайлов (хеш или ревизию профиля), чтобы не нарушать immutable-кеширование. Крупный исходный JPG сохранён в комплекте для совместимости, но при наличии raster браузер загружает обзорный JPG и тайлы.

## Firebase

Минимальный вариант: Cloud Storage/Hosting отдаёт manifest, JSON и ресурсы по HTTPS, клиент использует существующий HTTP-адаптер.

Realtime-вариант: новый адаптер реализует `MapRepository`, получает публичный manifest из `publicMaps/{zooId}`, загружает JSON из Storage и реализует `subscribe(onChange)` через `onSnapshot`. Уведомление означает повторное чтение указателя версии; источником истины остаётся manifest. SDK Firebase добавляется только при реальном подключении проекта.

Открытая карта читает только опубликованные данные. Сохранение черновика в админке и публикация для посетителей — разные операции. Аутентификация администраторов, Security Rules, права зоопарков и серверная публикация находятся на стороне админки/бэкенда. Секреты и service account нельзя помещать в VITE_*.

## Ограничения текущего этапа

Не подключены реальный Firebase-проект, чужая БД, геопривязка, публикация в домен и гарантированный офлайн. Подключаемый интерфейс и HTTP-загрузка реализованы, вместо имитации серверных интеграций.
